# 语速与时间轴对齐

## 为什么不能逐条字幕合成

字幕是按阅读节奏切的，一条常常只有 1–2 秒、5–10 个字，而且经常断在句子中间：

```
[12] 我就完全抛弃了
[13] 你一级调色里的饱和度
```

逐条合成会得到一串支离破碎的短句，每条都重新起调、重新收尾，听感像机器人念词条。正确做法是**先合并成语义完整的句块，再整块朗读**。

## 句块合并规则

按顺序累积字幕，遇到以下任一情况断开：

1. 当前文本以句末标点结尾（`。！？…`）
2. 与下一条的间隔超过 `--gap`（默认 0.5 秒）
3. 合并后超过 `--max-chars`（默认 45 字）

块内用「，」连接（原字幕往往没有标点），给 TTS 自然的停顿位置。合并后要清洗重复标点：`：，` → `：`，`，。` → `。`。

45 字 ≈ 7 秒，是「一口气读得完」和「对齐粒度够细」的平衡点。调到 60 字以上，句块动辄 10 秒，一旦读快了整段都提前结束，中间会空出一大截。

## 时间轴策略：加速 + 顺延

对每个句块，已知：

- `slot` = 下一块起点 − 本块起点（可用的时间窗，含块后的空档）
- `d` = 去掉首尾静音后的实际朗读时长

```
tempo = min(max_tempo, d / (slot - 0.04))   # 只在 d > slot 时生效
start = max(block.start, cursor)            # 上一句没说完就顺延
```

三个要点：

1. **只在超长时加速**，不主动拉伸。TTS 比原片快是好事，留出的空档听起来像自然停顿。
2. **加速上限 1.45**。超过这个倍率，齿音和元音会明显变形，宁可顺延。
3. **顺延而非截断**。截断会切掉字尾，顺延最多让画面和声音差几百毫秒，且遇到空档会自动复位，不会累积漂移。

实测一部 17 分钟、167 个句块的片子：平均加速 1.047x，仅 8 块顺延，最大 0.7 秒，片尾累计偏移 0。

## 语速的根源在风格提示

不要指望 atempo 解决语速问题。同一句话实测：

| 风格提示 | 时长 |
|---|---|
| 自然、口语化，语速中等偏快 | 5.76 s |
| 语速偏快、干脆利落，像视频博主边说边想 | 4.00 s |

差 30%。所以 `report.json` 里 `tempo_avg` 偏高时，先回去改 `--style`，重跑一遍比事后加速效果好得多。

推荐风格提示（中文技术讲解）：

```
语速偏快、干脆利落的中文口语讲解，像视频博主一样边说边想，
语气自然放松，不要播音腔，不要拖长音，英文术语按英文发音。
```

## 块内静音压缩

TTS 偶发超长内部静音，常见于数字、列表编号、特殊标点之后。检测到的最坏一次是 `"10."` 之后静默 7.9 秒。

处理链：

```
silenceremove=stop_periods=-1:stop_duration=0.30:stop_threshold=-40dB:stop_silence=0.18
→ areverse
→ silenceremove=start_periods=1:start_threshold=-45dB:start_silence=0.04
→ areverse
```

先压块内长停顿（保留 0.18 秒，听感上仍是停顿），再反转两次修掉首尾静音。`--max-pause` 可调，默认 0.30 秒——设太小会把正常换气也切掉，听感变得急促。

## 字幕必须按实际渲染时长反推

原字幕时间轴在合并、加速、顺延之后已经失效。正确做法：

1. 修剪后量出每块真实时长 `d`
2. 套用与拼接**完全一致**的 tempo 与 cursor 逻辑，算出真实起点
3. 在块内按字数比例分配，再切成单屏条目

因为 `atempo` 的输出长度是 `d / tempo`（采样级精确），所以不必重新渲染就能反推，误差小于 1 个采样。实测字幕边界与配音语音段的偏差在 0.2 秒以内。

## 字幕切分要保护英文词

硬按字符数切会把 `Color Boost` 劈成 `Color Bo` / `ost`。正确做法是先把文本 token 化成「英文词 / 空格 / 单个字符」，再按累积显示宽度切分——英文词作为整体不可分割。

显示宽度按 CJK 记 1、ASCII 记 0.55 估算，因为等宽字体下 ASCII 明显更窄。单条目标 18 个宽度单位，上限 26。
